# OVERRIDE implementation status — 2026-10-04

The product requirements are in `OVERRIDE_PRD_v0.3.docx`; `IMPLEMENTATION_PLAN.md` records the approved D1–D10 decisions and the complete acceptance criteria. This status tracks evidence without changing those requirements.

## Verified locally

- Pure 5×5 rules, Energy, simultaneous resolution, bots, match persistence, guest room authorization, Ranked queue/ready/settlement, rematches, and leaderboard service behavior have automated coverage. `npm test` passes 116 tests across 13 files, including deadline ordering, a two-connection action-lock race, absent-player grace at match start, valid same-round locks after a presence update, and Easy/Hard bot difficulty in resumed snapshots.
- Room and bot match creation use persisted request IDs so a retried request returns the original resource. A copy of the existing local SQLite database migrated to the new columns and indexes successfully.
- TypeScript and the production Vite build pass with `npm run build`.
- Two independent browser sessions joined a Quick Duel room. Reloading the host restored the open room with the original code; reloading during a newly joined match returned to the match screen. A solo Practice match and responsive views were exercised earlier in the local browser.
- A local two-session HTTP check completed all 15 Quick Duel rounds with fixed-deadline Pass actions, reached a draw, and started a rematch with swapped sides. This used synthetic guest sessions and is not human playtest evidence.
- A local WebSocket check confirmed that an open room socket marks its player present when a match starts and that switching to a match socket does not create a disconnect after the 1.5-second debounce. The same check failed before the fix.
- Browser keyboard checks confirmed that reveal and resignation use modal focus, Escape cancels resignation and restores focus to Leave match, and Next round focuses the new round label. The browser accessibility tree exposes board target coordinates and ownership as labeled controls; a human screen-reader check remains open.
- With reduced motion emulated in a browser, navigation from a scrolled How to Play page reached the top immediately; without that preference, the same navigation remained animated.
- A completed Practice result remained visible after a browser reload, with focus on its result heading. Selecting Home then reloading stayed on Home. This uses a per-tab match ID and a fresh authorized server snapshot; a finished match is not forced on a new tab.
- An open Quick Friend room was expired in the local database. The browser changed from Room open to Room expired and the Create new room action returned to the room form. Poll errors are now visible while a room ticket is open.
- A browser-driven Hard Practice match completed all 12 rounds with an Expand followed by explicit Pass actions. Every round showed its action reasons, including the final reveal before the result. The local fixture extended decision windows to permit browser automation; it did not change resolution rules. Refresh and rematch both retained Hard difficulty. A two-round fixture confirmed the reveal remains open after the next server decision starts, until the player selects Next round.
- A browser host and synthetic HTTP guest completed a one-round Quick Friend fixture: the guest's Ambush intercepted the host's Expand, both reasons appeared in the final reveal, and the requested rematch opened with sides swapped. This is local integration evidence, not a full 12-round human browser playtest.
- A synthetic signed-in browser profile displayed tier, official rank, rated match count, W-L-D, streak, and next Rival. The rename control updated the handle, and an immediate second rename showed the 30-day cooldown error. At a 320 px browser viewport, all seven stats and a maximum-length handle fit without horizontal scrolling or clipped heading text. Real Google sign-in remains unverified.
- A synthetic two-account browser check created a Ranked challenge, showed the creator's Ready prompt when the invitee accepted, and opened the same bound game for both players. This bypassed Google only for the local fixture; it does not verify real OAuth.
- A separate synthetic Ranked shell was set to 0% credit in the ignored local database. Before Ready, the browser disclosed that neither player's RP, rated matches, placement, W-L-D, or streak would change without revealing opponent identity. The bound game labeled the human opponent by handle; its terminal result showed +0 RP, unchanged rating, zero-credit explanation, tier, rank, next Rival, and New opponent/Leaderboard actions. The five settlement fields and four actions fit at 320 px without horizontal scrolling. This verifies display behavior, not the anti-farming assessment itself, which has service tests.
- In the production build, the same synthetic two-account flow ended by immediate resignation. Both browsers reached the correct result screens and showed complementary RP changes from one settlement. This check also exercised the race where settlement releases queue ownership before one client polls the active state.
- Refreshing the challenge creator before invite acceptance restored the same invitation link; acceptance then showed Ready on both browsers and proceeded to a bound match.
- The human leaderboard and Around You section were opened at 390 px and 320 px. The mobile navigation kept the Leaderboard link visible, and the document width matched the viewport without horizontal overflow.
- A file-backed restart test leaves a terminal Ranked match unsettled, reopens the database, and verifies one settlement and released ownership. Startup also reconciles lost WebSocket presence before overdue rounds resolve.
- A temporary profile-write failure over three settlement attempts now leaves the bound Ranked result and ownership pending. After recovery, one settlement commits and ownership releases; a separate missing-credit test still voids an untrustworthy result without changing ratings. The settlement worker remains available when a database query fails, and retry logs are limited to the first and every 60th failure.
- In a production-build browser fixture, an unsettled Ranked result showed a pending message and withheld rematch. Removing the write failure populated the RP change and rematch actions automatically. A separate invalid result changed from pending to Match voided without a reload.
- Retention tests remove old Ranked invitation tokens, including accepted invitations, while preserving Ranked match and settlement audit records.
- `npm run report:metrics`, `npm run ops:status`, and `npm run backup:db` run against the local database. The backup command checks SQLite integrity, and a copy was opened successfully at a fresh restore path. The health endpoint now returns 503 for database failure or overdue server work; operations output lists failed settlement retries and attempts to settle an already settled match. Local metrics contain test traffic and are not playtest conclusions.

2. Configure a Google OAuth Web client ID for the real public origin. Verify two distinct real accounts, sign-in return to a challenge, ready/binding, settlement, rematch, and leaderboard placement on desktop and mobile.
3. Deploy one server process with HTTPS and persistent SQLite storage to a production-like staging environment. Rehearse backup restoration there, then run the complete PRD §43–45 checks and an unfamiliar-reviewer demo across two devices, including screen-reader and network-flap checks.
4. Review traffic limits and the 30-day guest retention policy against the chosen host and expected launch volume. Add an edge rate limit before public access.

No public-launch or human-playtest claim is made by the local checks above.
